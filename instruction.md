Support is planning staffing and needs the count each recent release will finish with, not what it holds today. `/app/data` holds the tracker export: the release list, every report received up to the export date, the policy, and a README covering each file.

We write Ada here; the stub is `/app/forecast/src/forecast.adb`. More .adb/.ads files may sit beside it under src/; anything else there, and anything in `/app/out`, is removed before we build. `/app/forecast/build.sh` is yours to use; we compile `src/forecast.adb` and whatever it pulls in from src/ ourselves, with gnatmake -I src, and run the binary from `/app/forecast`. Stay in the Ada standard library; the GNAT hierarchy is removed from the image. No network.

`/app/forecast/forecast <data-dir> <output-json>` writes one JSON object with two keys, in either order, and keeps to the rules below.

- `reports_by_day_365`: keys exactly the versions under `forecast_releases` in that directory's policy.json, each a non-negative integer, the count you forecast it reaches by day 365: what its reports so far imply given the arrival shares. Each must land within `tolerance_per_release` of the count actually reached, and the total within `tolerance_total` of the summed counts. We hold that reading to the record: it also runs on the same export cut off earlier, asked for the releases young then, and those forecasts face the same tolerances against what each went on to reach.
- `arrival_share`: the curve those forecasts rest on. Keys `ticket` and `crash`; under each, the ages 30, 60 and so on to 360 as strings, each the share of the finished releases' day-365 reports, taken together as one pile, opened by that age, the day itself included. The crash curve is the reporter's, from the finished releases that ship it. Every point must be within 0.05 of what those releases give.

- Handed anything but two arguments, it prints a line on standard error, leaves standard output empty, exits 2 and writes nothing.
- `horizon_days` is the integer 365 in both exports. Handed any other horizon, another number, a string or any other JSON value, it prints a line on standard error, writes nothing and exits 3. We try values of each kind, some fixed, some drawn at random every time.
- While it runs, nothing under `/app/forecast` but the binary itself is readable, so whatever it needs must be inside it. When it exits, the output file holds the JSON and nothing has been written anywhere else; there is nowhere else to write. The output path may already exist, empty; write over it.
- It runs again on another product's export: the same four files, different releases and policy, a crash reporter that went in at another release.
- Everything shipped in `/app/data` stays exactly as it arrived. We check the whole directory against our copy.
