Support is planning staffing for the next two quarters. They need the count each recent release will finish with, not what it holds today. The tracker export is in `/app/data`: the release list, every report received up to the export date, the policy, and a README covering each file.

We write Ada here. There is a stub at `/app/forecast/src/forecast.adb`. You can split the program across more `.adb`/`.ads` files next to it under `src/`. The build script at `/app/forecast/build.sh` is for your own use; we compile the source ourselves.

- `/app/forecast/forecast <data-dir> <output-json>` writes one JSON object with two keys, in either order. Given any other number of arguments it prints a line on standard error, leaves standard output empty, exits 2 and creates no output file.
- `arrival_share` has two keys, `ticket` and `crash`. Under each, the ages 30, 60, 90 and so on in thirty-day steps up to 360, written as strings, each a share between 0 and 1. Build it from the releases in the export at least 365 days old; the crash curve only from the releases in that cohort whose `crash_reporter` column says yes, whatever is filed against one that doesn't. For each source, add up its open reports with an opened lag under 30 days, under 60, and so on, over that cohort, and divide by its open reports the same cohort held by day 365. Both cohorts always have reports in by day 365, so none of these shares is a divide by zero. Every point must land within 0.05 of ours.
- `reports_by_day_365` has keys exactly the versions listed under `forecast_releases` in the given directory's policy.json, mapped to non-negative integers. Every release we ask about is at least a month old, so it always has at least one complete thirty-day column: a release A days old holds floor((A+1)/30) of them, so a 100 day old release has three. That count tops out at twelve: a release 359 days old or older still uses the twelfth column, the 360-day one, since the curve stops there, and that holds even for a release support kept on the list after it already finished collecting. Take the release's last complete column, N days: count its open reports from one source with opened lag under N, divide by your curve's N-day figure for that source, do the same for the other source, and add the two. We check each forecast against the curve you printed, taking each share as exact only to its last printed digit, and it has to agree within one report.
- Every report row also carries `status` (`open`, `duplicate` or `invalid`) and `opened_date`. Drop any report that is not `open` from every count and curve. Compute a report's lag from `opened_date`, never from `reported_date`.
- `horizon_days` is 365 in both exports. If a policy asks for another horizon, print a line on standard error, create no output file and exit 3.
- Stay in the Ada standard library; the GNAT hierarchy is removed from the image. No network. We build only `src/forecast.adb` and whatever it pulls in from `src/` with `gnatmake -I src`, then run that binary from `/app/forecast`.
- Before each run everything under `/app/forecast` other than the compiled binary is made unreadable and not executable, the build script included, so that part is ours to keep clean. If your program writes a new executable file anywhere it can reach while it runs, or leaves any new file under `/app` other than the JSON we asked for, that run's output is thrown away, so whatever it needs has to already be inside the binary.
- It runs again, unchanged, on another product's export: three files and a README in the same format, different releases and policy, and a crash reporter that went in at a different release.
- Everything shipped in `/app/data` stays exactly as it arrived. Nothing added, nothing removed, nothing changed. We check the whole directory against our copy afterward.

We score forecasts against the count each release actually reached by day 365. Every forecast release must land within `tolerance_per_release` of its count, and the total across those releases within `tolerance_total` of the summed counts. Both are fractions of the count, so 0.2 means twenty percent; the other product's policy carries different figures.
