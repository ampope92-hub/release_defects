Support is planning staffing for the next two quarters. They need the count each recent release will finish with, not what it holds today. The tracker export is in `/app/data`: the release list, every report received up to the export date, the policy, and a README covering each file.

We write Ada here. There is a stub at `/app/forecast/src/forecast.adb`. You can split the program across more .adb/.ads files next to it under src/; anything else there, and anything in `/app/out`, is removed before we build. The build script at `/app/forecast/build.sh` is for your own use: we compile `src/forecast.adb` and whatever it pulls in from src/ ourselves, with gnatmake -I src, and run the binary from `/app/forecast`. Stay in the Ada standard library; the GNAT hierarchy is removed from the image. No network.

`/app/forecast/forecast <data-dir> <output-json>` writes one JSON object with two keys, in either order, and keeps to the rules below them.

- `reports_by_day_365`: keys exactly the versions listed under `forecast_releases` in the given directory's policy.json, each mapped to a non-negative integer, your forecast of the count that release reaches by day 365. We score it against the count the release actually reaches: every forecast must land within `tolerance_per_release` of its count, and the total across those releases within `tolerance_total` of the summed counts. Both are fractions of the count; the other product's policy carries different figures.
- `arrival_share`: the curve those forecasts rest on. Keys `ticket` and `crash`; under each, the ages 30, 60, 90 and so on in thirty-day steps to 360, written as strings, each the share of a release's day-365 count that has been opened by that age, as the finished releases in the export show it. The crash curve is the crash reporter's, read off the releases that ship it. Every point must land within 0.05 of what those releases give.

- Handed any number of arguments other than two, it prints a line on standard error, leaves standard output empty, exits 2 and creates no file.
- `horizon_days` is 365 in both exports. Handed a policy that asks for any other horizon, it prints a line on standard error, creates no output file and exits 3.
- While it runs, nothing under `/app/forecast` but the binary itself is readable, so whatever it needs has to be inside the binary. A run may create nothing but the JSON it was asked for; if it leaves any other new file behind, anywhere it could write, that run's output is thrown away.
- It runs again on another product's export: three files and a README in the same format, different releases and policy, and a crash reporter that went in at a different release.
- Everything shipped in `/app/data` stays exactly as it arrived. We check the whole directory against our copy afterward.
